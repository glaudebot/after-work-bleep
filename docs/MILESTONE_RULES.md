# 작업 방식

## 진행 순서
주제를 받으면 아래 순서로 진행하고, 단계마다 멈추고 확인받는다.

1. **정의서:** 내 설명으로 docs/spec.md 초안을 쓴다. 모호한 부분은 추측하지 말고
   "정할 것" 목록으로 정리해 추천안과 함께 묻는다. 승인받으면 확정.
2. **기본 문서:** 이 작업 방식 전체를 docs/MILESTONE_RULES.md 로 저장하고,
   CLAUDE.md, docs/decisions.md, STACK.md, TODO.md, docs/qa/QA_CHECKLIST.md 를 만든다.
   - CLAUDE.md: 한 줄 소개, 문서 표, 구조·스택 요약, 실행 명령, 아래 "작업 규칙". 길게 쓰지 말고 링크로 연결.
   - decisions.md: spec.md에서 확정된 결정을 D-01부터, 출처(spec.md 장 번호)와 함께.
   - QA_CHECKLIST.md: spec.md의 완료 조건·테스트 시나리오에서 시작.
3. **마일스톤:** 전체 개발을 N개 마일스톤으로 나눈다.
   - 마일스톤 하나 = 내가 직접 실행해서 눈으로 확인할 수 있는 결과 하나. "DB만", "API만" 같은 건 안 된다.
   - 기본 5~8개. 벗어나면 이유를 설명한다.
   - 외부 조건(권한, 계약, 심사 등)으로 못 하는 작업은 별도 마일스톤으로 두고 ⛔ 대기.
   - 먼저 표(번호, 이름, 한 줄 목표, 사용자 확인 결과, 예상 꼭지점 수)로 보여주고 승인받는다.
   - 승인 후 MILESTONES.md, 모든 M<n>.md, 첫 마일스톤의 꼭지점 문서만 만든다.
4. **개발:** "다음 꼭지점 진행해줘"라고 하면 꼭지점 하나씩 개발한다 (아래 작업 규칙).

## 문서 구조
```
MILESTONES.md                    ← 색인: 단계·마일스톤·상태, 변경 기록
└─ docs/milestones/M3.md         ← 마일스톤: 목표, 완료 조건, 꼭지점 색인, 마감 기록
   └─ docs/milestones/M3-1.md    ← 꼭지점 = 개발 단위: 정해진 것·정할 것·손댈 곳·체크리스트
docs/spec.md                     ← 기준 정의서
docs/decisions.md                ← 설계 결정 원장 (D-번호)
docs/qa/QA_CHECKLIST.md          ← 마감 때 돌리는 점검 항목
STACK.md                         ← 실제 스택·버전과 변경 이력
TODO.md                          ← 아직 꼭지점에 안 들어간 결정·요청·보류
```
- 상위 문서는 하위 문서의 색인만 가진다. 체크리스트는 꼭지점 문서에만 있다.
- 꼭지점을 진행할 때는 그 문서 하나만 읽는다. 그래서 꼭지점 문서에 결정 요지, 현재 구조,
  손댈 파일을 담아 그것만 보고 작업할 수 있게 한다. 모자란 정보는 읽어 온 뒤 꼭지점 문서에 보충한다.

## 핵심 원칙
1. **완료 조건:** 마일스톤마다 "사용자 확인 결과"와 "통과할 QA 항목 번호"를 적고, 그걸로 마감한다.
2. **결정 ID:** 결정은 decisions.md에 D-번호로 쌓는다. 꼭지점에는 요지만 적고 `(D-07)`처럼 출처를 단다.
3. **번호 고정:** 붙인 마일스톤·꼭지점·D 번호는 바꾸지 않는다. 끼워 넣을 때는 `M3.1`, `M3-2a`.
4. **⛔ 대기:** 외부 조건으로 못 하는 마일스톤은 ⛔ + 막힌 이유.
5. **스택 기록:** 런타임·라이브러리·설정·환경변수가 바뀌면 그 자리에서 STACK.md와 꼭지점 Stack 항목에 적는다.
6. **필요할 때 만든다:** 다음 마일스톤의 꼭지점 문서는 그 마일스톤을 시작할 때 만든다.

## 표기
- 상태: ✅ 완료 · 🔨 진행 중 · ⏳ 예정 · ⛔ 대기
- 체크리스트 4관점: Back(서버·API·DB) · Front(화면·클라이언트) · Test(자동 테스트·실행 확인) · Stack(의존성·설정).
  프로젝트에 맞게 이름을 바꿔도 되지만 4개 이내. 항목 하나 = 확인 가능한 결과 하나, 없으면 `- 해당 없음`.
- 결정·지시에는 날짜: `(YYYY-MM-DD 사용자)`

## 작업 규칙
- 개발은 꼭지점 단위.
- 착수 전에 "정할 것"을 선택지 + 추천안(이유)으로 묻는다. 답을 받으면 "정해진 것"으로 옮기고(날짜),
  필요하면 decisions.md에 D-번호를 추가한 뒤 개발한다.
- 새 화면·기능은 착수 전에 화면 구성을 글로 정리해 확인받는다. 목업은 요청할 때만.
- 꼭지점이 크면 "단계" 표로 나눠 한 단계씩 진행하고 확인받는다.
- 항목을 끝낼 때마다 체크리스트를 갱신한다.
- 꼭지점 끝: 바꾼 영역 테스트 + 타입 검사 + 빌드 → 꼭지점 ✅ → 마일스톤 색인 갱신 → 커밋 → `/compact` 권장.
- 다음 마일스톤을 시작할 때는 그 마일스톤의 꼭지점 문서들을 먼저 만들고 목록을 승인받는다.
- 마일스톤에 안 들어간 요청·보류·QA 지적은 TODO.md에, 반영하면 지운다.
- 작은 판단은 가장 단순한 방식으로 정하고 꼭지점 문서에 기록. 큰 설계 판단은 멈추고 묻는다.

## 마일스톤 마감
1. 모든 꼭지점 ✅ 확인
2. QA_CHECKLIST.md 전체 실행 → 결과를 마일스톤 문서 "마감" 절에 기록 (FAIL은 고친 뒤 마감)
3. "사용자 확인 결과"를 나에게 확인 요청
4. 새 기능에 맞춰 QA_CHECKLIST.md 항목 추가
5. MILESTONES.md 상태 ✅ + 날짜 → 커밋

```markdown
# 마일스톤

(규칙은 docs/MILESTONE_RULES.md)
## 색인
| 단계 | 마일스톤 | 사용자 확인 결과 | 꼭지점 | 상태 |
|---|---|---|---|---|
| 0. 기반 | [M1](docs/milestones/M1.md) 이름 | 실행하면 보이는 것 | 3 | ⏳ 예정 |
## 변경 기록
> YYYY-MM-DD: 무엇을 왜 바꿨는지
```
